CSP 인지 부채 감사

기준일 2026-07-04 · 대상 head-repo\hw725\CSP · 마지막 커밋 2026-02-26 (d64772f) · 미커밋 변경 15건. 이 문서는 "코드는 존재하지만 내 이해가 따라가지 못한 지점"의 지도다. 유지보수문서 01이 이미 다루는 내용(P2S/S2P 알고리즘, worktree 원격 분리)은 반복하지 않는다.

1. 배경 — 이 프로젝트가 실제로 하는 일

CSP는 한문 원문과 한국어 번역문을 문단 → 문장 → 구 세 층위에서 1:1로 정렬하는 파이프라인이다. 다만 유지보수문서가 "XLSX 문단 병렬본을 입력받아"라고 서술하는 것과 달리, 2026년 2월 말부터의 실제 작업은 그 앞 단계, 즉 고전번역원 XML(sources/, 134개 파일·92MB)에서 3종 병렬 XLSX를 뽑아내는 추출 계층에 집중되어 있었다. 미커밋 15건 전부가 이 계층(xlsx_scripts/, xml_pipeline/, xml_extractor/)에 몰려 있다.

2. 직관 — 3층 구조로 기억하라

  1. 추출층 (최근 활동, 절반쯤 커밋됨): sources/ XML → xlsx_scripts/ 6단계 워크플로우 → xlsx/ 44권 폴더에 문단·문장·구병렬 XLSX 생성.
  2. 정렬층 (문서화 잘 됨, 안정): batch_44books.py가 책마다 P2S(문단→문장, BiLSTM 경계 + BGE 정제) → S2P(문장→구, Viterbi + Punctuation Guard) 실행 → xlsx_pipeline_results/.
  3. 분석층 (거의 미문서화): hyeonto/ — 추적 파일 127개로 repo에서 가장 큰 모듈. 현토 마커 클러스터링, 공기 네트워크, LLM 검증(Triple-Threat), 대시보드 서버(md_server.py).

3. 핵심 흐름

점선 상자·화살표 = 위험 또는 암묵 의존. 진입점 main.py는 이름과 달리 XML 계열 전용 래퍼이며, XLSX 정렬의 실제 진입은 batch_44books.py·p2s/main.py·s2p/main.py다.

4. 핫스팟 위험 순위표

#위험핫스팟 (경로)무엇이 문제인가지금 이해하지 않으면 나중에…
1높음 xml_extractor/ (git 미추적) 완전히 새 모듈인데 untracked. 그런데 미커밋 상태의 xml_pipeline/__init__.py가 여기서 XMLProcessor, XMLPair 등을 import하도록 이미 수정됨. git clean -fd 한 번, 혹은 폴더 정리 중 삭제 한 번이면 복구 불가(백업 없음)이고 xml_pipeline 전체가 import 에러로 죽는다.
2높음 xml_pipeline/xml_pipeline_processor.py (−394줄 unstaged) + xlsx_scripts/ 9개 (staged) 추출 로직을 xml_extractor로 이관하는 리팩터가 4개월째 반쯤 커밋된 채 정지 (마지막 커밋 2026-02-26). staged만 커밋하거나 unstaged만 되돌리면 절반씩 다른 세계가 된다. xml_pipeline 수정 + xml_extractor 신규 추적을 한 세트로 커밋해야 클론이 동작한다.
3높음 git 브랜치 상태 (main ↔ csp/main) 11 ahead / 11 behind 분기. 양쪽 HEAD 커밋 메시지가 동일("xml_pipeline 복구") — 같은 작업이 로컬·원격에 따로 커밋된 흔적. 정체불명 codex/pre-rebase-5ec5931 브랜치도 존재. 급하게 push하면 거부되고, force push하면 원격 11개 커밋이 소실된다. 어느 쪽이 정본인지 비교·정리 없이는 백업(push) 자체가 불가능한 상태가 지속된다.
4높음 xlsx_scripts/README.md의 유령 스크립트 특수 서종 4권(예기집설대전1, 당시삼백수1~3)의 처리기로 지시된 extract_yeogi.py·create_yeogi_paragraph.py가 repo 어디에도 없음 (2025구축 상위 3단계에서도 미발견 — 소재 미확인). 특수 4권은 <단락 id> 구조라 일반 스크립트가 처리 못한다. XML에서 XLSX를 재생성해야 하는 날, 4권만 만들 방법이 없다.
5중간 jti_code_mappings.py·xml_unit_parser.py·xml_file_browser.py xml_pipeline/과 xml_extractor/에 md5 동일 사본 3쌍. 어느 쪽이 canonical인지 미확정 (리팩터 방향상 xml_extractor로 추정). 한쪽만 고치면 조용히 갈라져서, 실행 경로에 따라 다른 결과가 나오는 재현 불가 버그가 된다.
6중간 common/config.py + csp_config.json 설정 우선순위가 json ≻ 환경변수. device: "cuda:0"이 json에 하드코딩되어 CSP_DEVICE 환경변수로 못 덮는다. API 키는 json이 null이라 .env로 폴백. GPU 없는 로컬이나 새 환경에서 "환경변수를 설정했는데 왜 안 먹지"로 시간을 잃는다. Docker(PyTorch 2.6.0)와 로컬(2.9.1) 버전 차와 겹치면 재현 실패 원인 추적이 배로 어려워진다.
7중간 hyeonto/ (추적 127개 파일) repo 최대 모듈인데 README 없음. 유지보수문서 01에는 md_server.py 한 줄만 언급. 분석 스크립트 30여 개의 실행 순서·의존 관계 미기록. 논문 수치의 산출 경로(어느 스크립트가 어느 데이터로 어떤 그림을 만들었나)를 재구성할 수 없게 된다 — 투고·심사 대응 시 가장 비싸지는 부채.
8낮음 renumber_excel_indices.py 원본 XML 식별자(ID:W1 등)를 1, 2, 3… 연번으로 덮어씀. 이 단계 이후 XLSX 행을 원본 XML 위치로 역추적할 수 없다. 사료 충실성 감사가 필요해지는 순간 비용이 커진다.
9낮음 datasets/ 25GB · cache/ 6.5GB · models/*.pt 78MB 전부 git 밖 로컬 전용. 이 PC가 유일본. 디스크 장애 시 gold standard·학습 가중치·임베딩 캐시 전부 소실. 모델은 재학습(H200 ~5.2h+) 비용, gold standard는 재구축 비용.

5. Drift 로그 — 유지보수문서 01의 서술 중 더 이상 정확하지 않은 것

  1. "XLSX 문단 병렬본을 입력받아" — 현재 실질 작업의 중심은 그 앞의 XML 추출층이다. 문서의 핵심 파일 표에 xlsx_scripts/·xml_pipeline/·xml_extractor/가 전혀 없다. 증거: 미커밋 15건 전부 + 마지막 커밋 d64772f(2026-02-26 "xml_pipeline 복구")가 모두 이 계층.
  2. "main.py — 파일형식 XML/XLSX/CSV/TXT 자동감지" — 과장. 실제 main.py의 txt·xlsx 서브커맨드는 "미래 지원" 스텁이고 동작하는 것은 xml·xml-merged·auto뿐. 증거: main.py의 "🚧 상세 처리는 향후 구현 예정" 출력.
  3. "44권" — batch_44books.py는 44권이지만, 새 추출 워크플로우(xlsx_scripts/README.md, staged)는 일관되게 43권(일반 39 + 특수 4)을 기준으로 한다. 1권의 차이가 무엇인지 미기록(미확인).
  4. 워크트리 origin 분리 서술은 여전히 사실이나, 문서에 없는 브랜치 codex/pre-rebase-5ec5931이 존재하고, dansa-research 브랜치는 csp/main 대비 59 ahead / 97 behind로 더 벌어졌다. 증거: git branch -vv.
  5. 문서 작성 이후 생긴 것들: xml_extractor_results/·xml_pipeline_results/(untracked 결과 폴더), xml_extractor/toc_generator.py·toc_dashboard.py(2026-06-10 수정 — 커밋 없는 6월 작업의 증거), sources/ 디렉토리 자체(2026-06-09 갱신). 문서 01은 sources/를 "2025구축이 참조하는 경로"로만 언급하고 CSP 자신의 입력이라는 사실은 누락.
  6. 미커밋 상태 자체가 문서에 없다 — 문서는 repo가 정지 상태인 것처럼 읽히지만, 실제로는 staged 1,372줄 + unstaged −394줄의 리팩터가 걸려 있는 "작업 중단" 상태다.
